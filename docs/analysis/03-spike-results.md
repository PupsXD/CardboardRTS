# Спайк симуляции: что построено, что проверено, что нет

Код: [`packages/sim`](../../packages/sim). Это не игра, а ядро разрешения хода, чтобы утверждения в остальных
документах опирались на запущенный код. Дата: 2026-10-10.

**Версии.** Сейчас в `main` — **непрерывное пространство** (как в Lines of Battle; решение владельца).
Первая версия на клеточной сетке (8 направлений, 36 тестов) сохранена тегом
[`spike-grid-v1`](https://github.com/PupsXD/CardboardRTS/tree/spike-grid-v1); её данные ниже приведены только для сравнения.

## Что внутри

| Файл | Роль |
|---|---|
| `src/types.ts` | Состояние, приказы (`move` / `attack` / `defend` **группе юнитов**), события, константы (`SCALE`, рельеф) |
| `src/geom.ts` | Целочисленная геометрия: `isqrt`, `advance` (движение по ломаной), скорость по рельефу |
| `src/collide.ts` | Расталкивание тел (итерации Якоби), твёрдые клетки рельефа, `maxOverlap` |
| `src/resolve.ts` | `resolveTurn` (валидация + AP, залпы, тики движения), `applyEvents`, `previewMove` |
| `src/fog.ts` | `filterEventsFor` (лог хода глазами игрока), `visibleUnits` |
| `test/` | 32 теста (Vitest) |
| `bench/bench.ts` | Замер 4 / 16 / 32 / 64 игроков |

**Как устроен ход.** Координаты — целые «пункты» (100 пунктов = 1 единица длины, диаметр юнита = 1 единица). Ход = 10 тиков.
В каждом тике: залп (если пора по режиму атаки) → одновременное движение всех → расталкивание тел. Только целочисленная
арифметика, поэтому результат побитно одинаков на любой машине и не зависит от порядка вычислений.

**Что выбрано условно** (заглушки, чтобы был код, это решения владельца — см. [OWNER-QUESTIONS](../OWNER-QUESTIONS.md)):
10 тиков на ход, скорость 30 пунктов/тик, радиус тела 50, дальность 300, обзор 500; рельеф растром 2×2 единицы
(дорога ×2, бездорожье ×0.6, стена); максимальный размер группы; приказ группе стоит 1 AP; движущиеся тела расталкивают
стоящих **без их смещения** (стоящий — «стена»); режим атаки `zone` по умолчанию; детерминированный урон без случайности.

## Проверено (команды `npm test`, `npm run typecheck`)

- 32 из 32 тестов проходят; `tsc --noEmit` (TypeScript 7.0.2) без ошибок.
- **Порядок входных данных не влияет на результат:** 150 случайных ходов × 3 режима атаки — перетасованные юниты и приказы
  дают тот же лог, состояние и статистику.
- **Лог полон:** `applyEvents(начальное состояние, лог)` совпадает с итогом (150 ходов × 3 режима).
- **Те же результаты при повторном запуске** бит в бит.
- **Границы:** юниты остаются в карте; остаточное перекрытие тел в разреженных сценариях ≤ 40 пунктов (допуск в тесте).
- **Скорость и рельеф:** 300 пунктов за ход по равнине, 600 по дороге, 180 по бездорожью (ожидания выведены руками из
  правил до запуска); излом ломаной проходится без потерь, недоход останавливает ровно на бюджете; превью совпадает с
  исполнением для одинокого юнита.
- **Расталкивание:** лоб в лоб строго по прямой — оба встают вплотную **симметрично** (сумма координат ровно 2400),
  никто не проходит насквозь; стоящий юнит при толчке не сдвигается ни на пункт; со смещением тела скользят мимо.
- **Стена — твёрдая:** юнит упирается вплотную (радиус 50), сквозь не проходит.
- **Группы:** группа из 5 стоит 1 AP; группа идёт со скоростью самого медленного и сохраняет построение
  (позиции после хода проверены точными числами); большая группа, чужие, дубли, пустая — отклоняются целиком.
- **Время залпа решает, можно ли уйти от выстрела** (числа выведены руками до запуска):
  `start` — цель, ушедшая за ход, всё равно получает 40; `end` — не получает; `zone` — получает 3 попадания по 4 = 12.
  Оборона в `zone` режет урон на тик 4 → 2 (стоящий в зоне весь ход: 40 против 20).
- Взаимное убийство, переубийство (3 стрелка по 50 hp: 70 урона зря), убитый в зоне не двигается и не стреляет.
- **Туман:** далёкое движение не попадает в лог вообще; при входе в обзор виден только видимый кусок, невидимое начало
  заменено на `null`; события со своими юнитами идут целиком; бой вдали виден только участникам.
- **Тесты чувствительны.** Мутации, которые тесты поймали: убрана сортировка стрелков по id (роняет 2 теста), в паре
  движущихся сдвигается только один (роняет тест на лоб в лоб).

### Что нашли сами тесты и бенчмарк (баги и уроки)

1. **Зависимость от порядка входа в событиях `blocked`.** Property-тест упал сразу на всех режимах: остановки писались в
   порядке массива движущихся. Исправлено сортировкой по id юнита. Без property-теста я бы этого не заметил.
2. **Откат при выталкивании в стену давал перекрытие тел до 95 пунктов из 100.** Движущийся юнит, зажатый между стоящим и
   стеной, откатывался на позицию до расталкивания, то есть внутрь соседа. Исправлено: стены теперь твёрдые тела для
   расталкивания, а не только проверка центра. Увеличение проходов расталкивания с 4 до 12 перекрытие **не** уменьшало
   (проверено), значит, причина была структурной.
3. **Двойной счёт выталкивания на стыке клеток одной стены:** тело стояло на границе двух клеток сплошной стены и
   выталкивалось вдвое сильнее (остановка в 1120 вместо 1150). Исправлено: по каждой оси берётся наибольшее, а не сумма.
4. **Артефакт бенчмарка:** запуск всех размеров подряд в одном процессе давал в 4–8 раз худшие цифры (до 5 с на фильтр
   тумана), чем отдельный процесс на размер. Причина не выяснена (подозрение: прогрев JIT / сборка мусора). Дальше везде
   отдельный процесс.

### Сравнение с клеточной версией (`spike-grid-v1`, тот же бот-сценарий, другие приказы)

| | Клетки, 64 игрока | Непрерывно, 64 игрока |
|---|---:|---:|
| `resolveTurn`, мс | ~11–14 | ~70 |
| Фильтр тумана для всех, мс | ~120–170 | ~730 |
| Лог одному игроку, КБ | ~3.2 | ~24 |

Сравнение приблизительное (разная нагрузка: в клетках приказ на юнита и AP 30, в непрерывной — на группу и AP 8), но порядок
ясен: **непрерывное пространство дороже примерно в 5–7 раз по времени и в ~7 раз по размеру лога.** Во всех случаях это
единицы–доли секунды на ход при ходе в десятки секунд, то есть не препятствие для 4–16 игроков.

### Профиль и что с ним делать

CPU-профиль 64-игрочного прогона: ~80% времени — фильтр тумана (`sees`, `filterEventsFor`), расталкивание — ~4%.
Известный путь ускорения (не сделан): считать, кто видит событие, **один раз на событие** через общий пространственный
индекс всех юнитов, а не отдельным проходом на каждого игрока. Тогда стоимость перестанет расти с числом игроков.
Размер лога снижается отправкой траекторий (позиции по тикам дельтами) вместо события на каждый шаг каждого тика.

## НЕ проверено

- Никакого клиента, сервера, сети, базы данных. Выбор стека для них опирается на доводы, а не на прототип.
- Экономика, энергия, стройка, способности, шпионаж, исследования — в спайке их нет.
- **Остаточное перекрытие тел в плотных схватках** до 58 пунктов из 100 (в худшем ходу за 16): стоящие тела «стены» не
  смещаются, зажатый движущийся остаётся внутри. Способы лечения (мягкое смещение стоящих, больше проходов с весами)
  не проверены. Это же вопрос дизайна: «стоящий — неподвижная преграда» или «все расталкиваются».
- Баланс и «ощущение» игры: боты не играют осмысленно, цифры бенча — порядок величины.
- Память, GC при тысячах матчей, поведение при долгой работе; причина артефакта с прогревом (п. 4 выше).
- Нагрузка на соединения: 64 клиента в одной комнате живьём не пробовали.
- Тест `apply(filter(events), project(S_{N−1})) == project(S_N)` (см. [ROADMAP](../ROADMAP.md)) и тест неинтерференции тумана.
- Поиск пути: сейчас ломаную рисует игрок, ядро ей следует и упирается в стены. Автообход препятствий не реализован.
