# ADR 0002. Авторитетный сервер, лог по туману, снимки и версии правил

Статус: **предложено**. Дата: 2026-10-10. Связано: [ADR 0001](0001-tech-stack.md), [B5 в узких местах](../analysis/01-design-bottlenecks.md).

## Решение

1. **Сервер хранит полное состояние и один считает исход.** Клиент никогда не получает полного состояния.
2. **Ход закрывается** по «все подтвердили» или дедлайну. Приказы до закрытия хранятся на сервере и никому не показываются.
   Криптографическое «запечатывание» не нужно: сервер доверенный.
3. **Клиенту уходит:** проекция состояния для игрока (видимые юниты, своя экономика, дедлайн) и лог исполнения хода,
   отфильтрованный по тумане (`filterEventsFor`). Лог нужен для анимации, проекция — для реконнекта, нового устройства,
   входа на 40-м ходу.
4. **Персистентность — снимок на каждый ход.** Таблица хода: полное состояние (десятки КБ), приказы, сид, `rules_version`
   матча. Лог из приказов — **инструмент отладки и тестов детерминизма**, а не источник истины.
5. **Матч пиннится к версии правил.** Деплой новой версии не меняет идущие матчи; миграция только явная (преобразование
   состояния), а не пересчёт с нуля. (Причина: правка баланса или фикс в ядре делает пересчёт хода 37 другим — **[чужое мнение, принято]**.)
6. **Дедлайны хода — в БД** (`deadline_at`), а не в таймерах процесса. При старте процесс сканирует просроченные матчи и
   закрывает их. Дедлайны асинхронных матчей размазываются (джиттер), чтобы не закрывать сотни разом.
7. **Протокол не зависит от непрерывного соединения.** Источник правды для клиента: `GET /match/:id/view`
   (проекция + лог последнего хода). WebSocket/SSE — только уведомление «ход разрешён / твой ход».
8. **Матч как актор** с интерфейсом `submitOrders(player, turn, orders)`, `onDeadline(turn)`, `snapshot()`,
   `restore(snapshot)`, без прямого доступа к БД внутри: хранилище — адаптер. Дёшево сейчас, и даёт путь к другой среде.
9. **Идентификаторы.** Внешние id юнитов — непрозрачные для клиента (не глобальный счётчик): иначе по ним видно, сколько
   юнитов построил враг. Целью атаки служит клетка/область, а не id.
10. **Боты играют на проекции** для своего игрока, не на полном состоянии.
11. **Идемпотентность:** отправка приказов `(match, turn, nonce)`; повторная отправка до подтверждения заменяет план;
    после подтверждения не меняется.

## Что проверено, что нет

- **Проверено:** в спайке лог хода полон — `applyEvents(начальное, лог)` равен итоговому состоянию (150 случайных ходов × 3 режима атаки);
  размер лога одному игроку **~31 КБ** при 4–64 игроках (непрерывное пространство: событие на каждый шаг каждого тика),
  снимок всех юнитов 17–281 КБ (см. [03](../analysis/03-spike-results.md)). Лог можно ужать траекториями вместо шагов; не сделано.
  `node:sqlite` доступен в Node 24.19 без флагов.
- **Не проверено:** сервер, протокол, схема БД и нагрузка 64 соединений — их ещё нет. Тест
  `apply(filter(events, P), project(S_{N−1}, P)) == project(S_N, P)` пока не написан: нужна функция `project`
  и решение, какие данные несут события «появления» юнита.
- **Оценка, не измерение:** размер снимка на ход. Измерен только список юнитов в JSON: 17 КБ (4 игрока) … 281 КБ
  (64 игрока); экономика, здания и карта сюда не входят. При росте снимки можно сжимать или хранить дельтами.

## Что было отвергнуто

- Хранить только начальное состояние + сид + приказы (лог как единственная истина): ломается при любой правке правил,
  см. п. 5.
- Синхронизация состояния клиентам (в стиле Colyseus-схем): раскрывает невидимое или требует построчной фильтрации;
  лог по туману проще и доказуемо полон.
- Шардинг по match id сейчас: одна машина тянет большое число матчей по CPU (на синтетической нагрузке ход ~140 мс при 64 игроках, ~5 мс при 4);
  потолок по соединениям и памяти не измерен, шардинг — когда он будет измерен и достигнут.
- Вынос разрешения хода в `worker_threads`: измеренные ~140 мс на ход при 64 игроках (~5 мс при 4) не оправдывают сложность. Пересмотреть,
  если карты и армии станут на порядок больше или появится дорогая логика экономики.
