# ADR 0001. Технологический стек

Статус: **предложено** (решение принимает владелец; помечено, что проверено, а что нет).
Дата: 2026-10-10. Контекст: веб-игра, пошаговая тактика с одновременными ходами, разработчик один,
далее возможен массовый режим ([02](../analysis/02-mass-multiplayer.md)).

## Решение

| Слой | Выбор | Проверено? |
|---|---|---|
| Язык | TypeScript везде, один монорепозиторий (npm workspaces) | да, спайк собран и тестируется |
| Ядро правил | `packages/sim`: чистая детерминированная симуляция в **непрерывном пространстве** (целочисленные «пункты»), без IO и `Math.random`, групповые приказы | да, 34 теста, бенч ([03](../analysis/03-spike-results.md)) |
| Сборка/тесты | Vite 8, Vitest 5, TypeScript 7.0.2 (`tsc --noEmit`), Node 24 | версии по `npm view`; `tsc`, `vitest` и запуск `.ts` в Node без сборки **работают** в этом репозитории |
| Клиент, рендер | **2D, Phaser 4** (4.2.1) для карты; UI приказов — DOM поверх канваса; стиль «тетрадный лист» ([04](../analysis/04-grid-and-paper-style.md)) | **нет**, клиента ещё нет; см. «Риски» |
| Сервер | Node 24, Fastify 5 (REST: лобби, вид матча) + `ws` 8 (уведомления «ход разрешён») | нет |
| Хранилище | SQLite через встроенный `node:sqlite` (на одном узле); Postgres — когда появится второй узел | `node:sqlite` в Node 24.19 работает без флагов — проверено |
| Хостинг на старте | один сервер (VPS), один процесс | рассуждение |

## Почему так

1. **Одна симуляция на сервер, клиент, ботов и тесты.** Клиенту нужна та же логика для превью и валидации приказов
   (стоимость маршрута, радиус, AP). Две реализации разъедутся. Это главный аргумент за TypeScript и против «C# сервер +
   TS клиент». Проверенный факт: ядро в TS считает ход на 64 игроках за ~140 мс (непрерывное пространство), на 4 игроках за ~5
   миллисекунд ([03](../analysis/03-spike-results.md)), то есть для целевых 4–16 игроков выигрыша от более быстрого языка нет.
2. **Серверная авторитетность неизбежна из-за тумана войны и тайных приказов.** Клиент не должен знать полное состояние.
   Это исключает P2P-lockstep (при нём у каждого клиента полное состояние) и делает фреймворки синхронизации состояния
   (Colyseus-схемы, boardgame.io) малополезными: здесь синхронизируется не состояние, а отфильтрованный лог хода.
   **Детерминизм:** в правилах только целые числа (проверено: результат не зависит от порядка входных данных), поэтому
   клиентское превью и серверный исход не расходятся между средами.
3. **Ход раз в десятки секунд или в сутки — трафик ничтожен.** Не нужен ни UDP, ни собственный протокол; REST для
   «дай вид матча» и ws только как уведомление.
4. **Phaser 4, а не PixiJS.** Pixi даёт рендер, а камеру, тайлмап, сцены, отсечение, pan/zoom пришлось бы писать
   самим **[чужое мнение: неделя–две]**. Phaser 4 это включает, и вы уже используете Phaser 4 + TS + Vite в w1 (тот же
   пайплайн и знание). Тысячи клеток для обоих рядовая нагрузка.
5. **`node:sqlite` вместо Postgres на старте.** Игровая нагрузка крошечная; один файл БД проще бэкапить и
   разворачивать. Схема не зависит от БД ([ADR 0002](0002-server-authority-and-persistence.md)).

## Рассмотренные альтернативы

- **C#/.NET сервер (ASP.NET Core + SignalR).** Совпадает с вашим планом роста (.NET-бэкенд), но порождает вторую
  реализацию правил в клиенте либо тяжёлый WASM-рантайм. Вариант: оставить .NET для сервисов *вокруг* игры
  (аккаунты, рейтинги, платежи, матчмейкинг), ядро игры — на TS. Это решение владельца: если цель проекта —
  тренировка .NET, это шов, по которому её можно делать, не дублируя правила. См. [OWNER-QUESTIONS](../OWNER-QUESTIONS.md).
- **Colyseus 0.18.** Хороший фреймворк комнат реального времени; синхронизация схемы состояния здесь не нужна и мешает
  фильтрации тумана. Можно взять только как транспорт/матчмейкинг — выигрыш не доказан, не берём.
- **Durable Objects (Cloudflare).** Технически подходят очень хорошо (будильники, один актор на матч, гибернация сокетов),
  но цена: привязка к платформе, отладка, лимиты процессорного времени **[чужое мнение, цифры не сверены]**.
  Смягчение: матч оформлен как актор с интерфейсом `submitOrders / onDeadline / snapshot / restore` без прямых
  обращений к БД — тогда перенос механический.
- **PixiJS 8.22.** Равнозначен по производительности, дороже по трудозатратам. Вернуться, если Phaser окажется тяжёл.
- **three.js (ортокамера, плоские меши).** Нужен был бы для динамического света и «вставания» вырезанных фигур. Владелец
  2026-10-10: «картон» = игра на бумаге в тетради, 2D попроще, значит three.js не нужен. Десктоп возможен позже
  обёрткой веба (не проверялось).
- **Рендер, отделённый от правил.** В любом варианте рендер получает только события через тонкий «презентер»;
  ядро о рендере не знает, замена движка не затронет правила.

## Риски и условия пересмотра

- Phaser 4 не проверен на карте 100×100 с сотнями юнитов, зумом и DOM-UI. **Ворота:** однодневный прототип рендера
  (карта 100×100, 500 юнитов, pan/zoom, замер FPS) до основной разработки клиента. Провал → PixiJS.
- TypeScript 7 (нативный компилятор) очень новый; в этом репозитории `tsc --noEmit` работает, но совместимость с
  экосистемой плагинов не исследована. При проблемах — откат на последнюю 5.x/6.x без изменения кода.
- Один процесс Node: падение = недоступность. Для старта приемлемо; состояние в БД, дедлайны тоже, поэтому рестарт
  безопасен (ADR 0002).
